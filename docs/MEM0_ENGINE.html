1. What is established, and what still needs measurement

The subject is Mem0 open-source (OSS) Python SDK 2.2.1, clone commit b7ad69a (7 Oct 2026, pyproject.toml:7), read-only. It is the "v3 memory algorithm" (April 2026): one ADD-only extraction call, then hybrid retrieval (semantic + BM25 + entity). The managed Mem0 Platform is a different product that adds graph memory, temporal reasoning and decay; its code is not in the clone, only its documentation.

The published LoCoMo 92.5 is a Platform number, not an OSS number. The README says so itself: "Scores reflect Mem0's managed platform, which includes proprietary optimizations not available in the open-source SDK" (README.md:55). The clone's evaluation/ folder is an empty git submodule (.gitmodules points to mem0ai/memory-benchmarks), so no evaluation code or result file is available to read here. All benchmark figures below are quoted from documentation and from our own earlier analysis.

Headline facts

  • One LLM call per add() in the default (infer=True) path; no ADD/UPDATE/DELETE/NOOP decision call any more. [read] mem0/memory/main.py:942-971; migration guide: "add() events: Returns ADD only" (docs/migration/oss-v2-to-v3.mdx).
  • No graph database in OSS. The Neo4j/Memgraph integration was removed; the "entity store" is a second vector collection holding spaCy-extracted entity strings that point back to memory IDs. [read] main.py:558-580, docs/migration/oss-v2-to-v3.mdx.
  • No LLM call at search time. Query entities and BM25 lemmas come from spaCy; an LLM is only used if the caller opts into the LLM reranker. [read] main.py:1642-1745.
  • OSS refuses the temporal parameters: add(timestamp=...) and search(reference_date=...) raise ValueError ("Platform-only"). [read] main.py:817-818, 1446-1447.
  • The model asks for linked_memory_ids (lineage links) but the OSS code never reads them back. [read] grep of main.py finds linked_memory_ids only in the entity-store payload code, not in the extraction-response handling (lines 973-1041).

How the stores combine or rank at read time [read]

Three independent signals are fused in Python, not inside the database: a dense cosine search over the memory collection (candidate set), a BM25 sparse query over the same collection (scores only), and a similarity search over the entity collection (boosts only). score_and_rank sums them additively and divides by the maximum score reachable with the active signals (utils/scoring.py:94-119). No reciprocal-rank fusion, no learned weights. Section 8 gives the formula and a worked example.

3. Complete insertion flow: accepted messages to stored memory

All steps are in Memory._add_to_vector_store (main.py:881-1220); the async twin is AsyncMemory._add_to_vector_store (:2556). The code labels them "V3 phased batch pipeline" (main.py:918).

  1. Validate and scope

    Reject non-str/dict/list messages; build metadata and effective filters from user_id/agent_id/run_id; refuse timestamp; accept expiration_date. [read]main.py:760-879

  2. Phase 0: context

    Session scope string from the ids; load the last 10 stored messages from SQLite; flatten new messages to role: content lines. [read]main.py:920-923, storage.py:298

  3. Phase 1: retrieve existing memories

    Embed the whole flattened new-message text as a query and take the top 10 existing memories in scope. They are shown to the extractor with integer ids "0".."9"; the integer-to-UUID map uuid_mapping is built but never used afterwards. [read]main.py:925-940

  4. Phase 2: one LLM call

    System prompt ADDITIVE_EXTRACTION_PROMPT (plus AGENT_CONTEXT_SUFFIX when the scope has an agent_id and no user_id), user prompt built by generate_additive_extraction_prompt; response_format=json_object. An LLM failure raises LLMError (no silent empty result). Parsing tolerates code fences and falls back to extract_json. [read]main.py:942-986; prompts.py:468, 947, 1016

  5. Phase 3: batch embed

    One embed_batch over the extracted texts; per-text fallback on failure. [read]main.py:993-1005

  6. Phase 4-5: build records and hash-dedup

    MD5 of the text is compared with the hashes of the 10 retrieved neighbours and with the batch itself; matches are dropped. Surviving records get text_lemmatized (spaCy), created_at=updated_at=now, and attributed_to if the model supplied it. [read]main.py:1007-1041

  7. Phase 6: persist

    One batch insert, with one-by-one fallback; if nothing persists, raise VectorStoreError. One batched history row per memory with event ADD. [read]main.py:1047-1098

  8. Phase 7: entity linking (no LLM)

    spaCy extracts entities from each stored text; entities are deduplicated across the batch by lower-cased text; one batch embed; one search_batch against the entity collection; an entity is merged into an existing one if text matches exactly or cosine is at least 0.95, otherwise inserted; linked_memory_ids is extended. [read]main.py:1100-1204

  9. Phase 8: save messages

    The raw messages are written to SQLite and the table is trimmed to the latest 10 per scope. [read]main.py:1207; storage.py:257-296

Other write entry points [read]

  • add(infer=False): no LLM; each non-system message is embedded and stored verbatim as a memory with role and actor_id. main.py:882-916
  • add(memory_type="procedural_memory", agent_id=...): one LLM call with PROCEDURAL_MEMORY_SYSTEM_PROMPT, result stored as one memory. Marked "TODO: Remove ... in a future breaking release". main.py:853-864, 2007-2050
  • update(memory_id, text): caller-supplied text; re-embed, overwrite the payload, history row UPDATE, entity links rebuilt; no LLM. main.py:1829-1881, 2052-2112
  • delete(memory_id): remove point, history row DELETE (is_deleted=1), strip id from entity records. main.py:2114-2142

Calls per turn and per session [read]

The unit of cost is the add() call, not the "turn". The caller chooses whether to pass one turn or a whole session in one list. Each add() = 1 extraction LLM call, 2 to 3 embedding requests (the neighbour-retrieval query embedding, one batch for the new facts, one batch for new entities), and 1 vector search plus 1 entity batch search. Adding a 19-turn LoCoMo session in one call is one LLM call; adding it turn by turn is 19 calls, each with an 8k-token system prompt ([inferred]: 33.7k characters in prompts.py:468-944, about 8k tokens at 4 characters per token).

Exact schema of the extractor output [read]

{"memory": [
  {"id": "0", "text": "<15-80 words, self-contained>", "attributed_to": "user" | "assistant",
    "linked_memory_ids": [""]} ]}   (prompts.py:924-936)

Only text and attributed_to are consumed by the code (main.py:1017-1041). id is discarded and linked_memory_ids is ignored, so the cross-memory lineage the prompt asks for is lost in OSS ([read] by grep). The only cross-memory links that survive are the entity-collection back-pointers.

5. The write-time prompts in detail

5.1 ADDITIVE_EXTRACTION_PROMPT ([read] configs/prompts.py:468-944)

  • Role. "Your sole operation is ADD: identify every piece of memorable information and produce self-contained, contextually rich factual statements." (l.472)
  • Both speakers are sources. Extract from user and assistant messages; "Attribute correctly: use 'User' for user-stated facts" (l.488). Anti-echo rule: do not re-extract what the assistant merely restates (l.574, 682). In multi-speaker data the assistant role may be a real person, and the prompt has an example (Maria/Bailey) that extracts her facts (l.572, Example 12). This was clearly tuned for LoCoMo-style two-person chat.
  • Bias to recall. "When in doubt, extract. A slightly redundant memory is far less costly than a missing one." (l.578) A checklist asks for 5-15 memories on 10+ message inputs (l.912).
  • Quality rules. Contextually rich not atomic (l.608), transitions must name old and new state ("switched from almond milk to oat milk", l.612-618), 15-80 words (l.631), proper nouns, numbers, qualifiers preserved (l.640-666), no fabrication, no implicit attributes (l.679-680).
  • Temporal anchoring. "Observation Date ... is your ONLY temporal anchor"; resolve relative expressions against it and never against Current Date (l.524-540, 634-636).
  • Inputs. Summary, Recently Extracted Memories, Existing Memories, Last k Messages, New Messages, Observation Date, Current Date, optional includes/excludes/custom instructions (l.478-549).
  • Linking. Add related existing-memory ids in linked_memory_ids for same entity, updated preference, continuation, contradiction (l.692-701).
  • Model. Whatever config.llm is; default provider OpenAI, default model gpt-5-mini (llms/openai.py:40), temperature 0.1, max_tokens 2000 (configs/llms/base.py) [read]. Platform model stack is not disclosed.
What the OSS code does not feed this prompt. generate_additive_extraction_prompt is called with only existing_memories, new_messages, last_k_messages and custom_instructions (main.py:950-955). So Summary is empty, Recently Extracted Memories is [], and Observation Date defaults to today's date (_resolve_dates, prompts.py:1007-1013) because timestamp is refused. A benchmark that replays old conversations through OSS therefore gets relative dates resolved against the run date unless the harness puts the session date inside the message text. [read]

5.2 AGENT_CONTEXT_SUFFIX ([read] prompts.py:947-957)

Appended when the scope has an agent_id and no user_id: "Frame memories from the agent's perspective: 'Agent was informed that [fact]'". attributed_to still records the true source.

5.3 PROCEDURAL_MEMORY_SYSTEM_PROMPT ([read] prompts.py:326)

"You are a memory summarization system that records and preserves the complete interaction history between a human and an AI agent ... Every output produced by the agent must be recorded verbatim." Numbered steps with action, unmodified result and metadata. One call, stored as one record.

6. Transcript, scope identifiers and history

  • Scope. At least one of user_id, agent_id, run_id is required. Writes accept them as keyword arguments; search()/get_all() take them inside filters and raise on top-level use. [read] main.py:773-802, 1449-1475
  • Memory ids. Fresh UUID4 per memory. Hash is MD5 of the text. [read] main.py:1022, 1030
  • Speaker identity. Only on the verbatim path (actor_id from message name, role). On the inference path the model emits one flag, attributed_to = user or assistant. There is no subject/about-whom field. [read] main.py:899-901, 1038-1039
  • Raw transcript. Not retained beyond the last 10 messages per scope; the source turn is not linked to the memory (no provenance pointer, no dia_id). [read] storage.py:281-296
  • History. The SQLite history table keeps old and new text with event type and timestamps; it is an audit trail and is not consulted during extraction or search. [read]
  • Expiry. expiration_date (YYYY-MM-DD) is stored in the payload; expired points are skipped on search/get_all unless show_expired=True. [read] main.py:427-460, 1684

8. Hybrid scoring internals

Formula [read] (utils/scoring.py:60-139)

semantic  = vector-store score of the candidate (cosine for Qdrant)
bm25      = sigmoid(steepness * (raw_bm25 - midpoint)),   (midpoint, steepness) by number of query lemmas:
            ≤3: (5, 0.7)   4-6: (7, 0.6)   7-9: (9, 0.5)   10-15: (10, 0.5)   >15: (12, 0.5)
entity    = max over matched entities of  sim * 0.5 * 1/(1 + 0.001*(n_linked-1)^2),   sim ≥ 0.5
max_possible = 1 + (1 if any bm25 hit in the pool) + (0.5 if any entity boost in the pool)
combined  = min( (semantic + bm25 + entity) / max_possible , 1.0 )     only if semantic ≥ threshold

Worked example [inferred] (illustrative numbers, formula read in code)

Query has 5 lemmas, so midpoint 7 and steepness 0.6. A candidate has cosine 0.62, raw BM25 8.0, and its entity matched with sim 0.90 and 5 linked memories. bm25 = 1/(1+e^-0.6) = 0.646; entity = 0.90 × 0.5 × 1/(1+0.001×16) = 0.443; max_possible = 2.5; combined = (0.62+0.646+0.443)/2.5 = 0.684.

Consequences worth knowing [read]

  • The divisor depends on whether any candidate has the signal, so one candidate's BM25 hit changes the normalisation of all candidates in that query.
  • Entity boost is capped at 0.5 and fades for entities linked to many memories (quadratic penalty), which dampens hub entities such as the user's own name.
  • The semantic threshold gates before combining, so an exact-keyword memory with cosine below 0.1 cannot be rescued.
  • Scores are relative to the active signal set, so the same memory can score differently with and without fastembed or spaCy installed (the migration guide says both are optional extras).

Protocol caveats [read]/[inferred]

  • Retrieval budget. top_200 memories per question (about 7k tokens), versus the engine default top_k=20 (main.py:1397). The vendor result is not the default-configuration result.
  • Category 5. Excluded (1,540 questions = categories 1-4). No published adversarial/abstention score.
  • Judge prompt. Mem0's binary ACCURACY_PROMPT (in memory-benchmarks, not in the clone) is the community default; its leniency is documented in our SOTA analysis (judge choice alone moves systems up to 18 points).
  • Evaluation code absent. evaluation/ is an empty submodule; the answer prompt, question-time rewrite and the benchmark-side date handling cannot be inspected from this clone. The docs say "Scores carry a +/-1 point confidence interval due to judge inconsistency" and "single-pass retrieval ... no agentic loops".
  • Platform vs OSS. The README states OSS users "should expect directionally similar gains but not identical numbers". The harness supports --backend oss, but no OSS-only result is published in the clone.

13. What to check to understand and verify the engine (nothing here was executed)

  1. Confirm the version: pyproject.toml:7 should read 2.2.1 and mem0/memory/main.py:918 should contain "V3 PHASED BATCH PIPELINE".
  2. Install the optional extras the retrieval path depends on: mem0ai[nlp] with en_core_web_sm (spaCy, Python 3.10-3.12) and fastembed for Qdrant BM25. Without them search silently degrades to semantic only (main.py:543-550; migration guide).
  3. Run search(..., explain=True) to see semantic_score, bm25_score, entity_boost, max_possible_score for each result (scoring.py:126-135).
  4. To replay historical conversations, put the session date inside the message text (the engine cannot take a timestamp) and record this as a protocol deviation.
  5. Reproduction harness: github.com/mem0ai/memory-benchmarks (--backend oss, --top-k 200, --top-k-cutoffs 10,20,50,200), per docs/core-concepts/memory-evaluation.mdx. Report the cutoff, judge and answer model with every number.

14. Implementation findings and limits

  • Linking is requested but dropped. The prompt spends ~10 lines and Example 10 on linked_memory_ids; the code ignores it, and uuid_mapping is dead. [read]
  • Prompt and code disagree on ids. The prompt says existing ids are UUIDs (l.508-513) while the code passes "0".."9" (main.py:940). [read]
  • Summary and recent-memory inputs are never filled in OSS, so two of the prompt's seven inputs are always empty. [read]
  • Observation date is the run date. Historical replay needs a harness workaround. [read]
  • Candidates come only from the dense leg. A fact reachable only by keyword or entity is lost. [read]
  • Hash dedup is exact. Only identical text is dropped; near-duplicates rely on the model's own dedup against ten neighbours. [read]
  • Entity listing cost. Each add lists up to 10,000 entity rows to detect exact matches (main.py:589), which will not scale linearly to large scopes. [inferred]
  • No speaker/subject model. One binary attributed_to; third-party facts and who-said-it are folded into text. [read]
  • Telemetry and notices. The SDK captures telemetry events and fetches a remote notices config unless disabled (memory/telemetry.py, notices.py:20-23). [read]
  • Evaluation code is absent from the clone; all published figures are unreproducible from here.

16. What MemSpine can learn from Mem0 (brief; the 4-way comparison comes later)

  • Zero-LLM read path with three cheap signals. Dense + lemmatised BM25 + entity back-pointer boost, fused additively with explainable score_details. If MemSpine's entity leg needs an LLM or graph hop, a spaCy/GLiNER entity-to-memory-id index is a cheaper first pass. The additive formula with an adaptive divisor is trivially portable.
  • Anti-hub entity penalty. 1/(1+0.001(n-1)^2) down-weights entities linked to many memories; a direct fix for "user name" dominating boosts.
  • Write-time dedup context. Show the extractor its top-10 neighbours and the last-10 messages; cost is one embedding and one search. Combine with MemSpine's supersede/merge so the neighbour set drives a typed integration, which Mem0 now throws away.
  • Transition-aware fact phrasing. "switched from X to Y after Z" captured in one fact is a cheap way to keep old-to-new links when no supersede machinery exists; MemSpine can use the same instruction to seed a supersede candidate.
  • Anti-hallucination ids. Mapping UUIDs to small integers before prompting (main.py:935-940); worth keeping, but unlike Mem0 actually consume the returned links.
  • Fail loudly. LLM extraction errors raise instead of returning an empty list (main.py:965-971); important for benchmarking honesty.
  • Counter-lesson (what to avoid). The headline 92.5 is a Platform, top_200, gpt-5 number; the same engine scores 77.7 in a neutral harness and 48.9 under a strict judge. MemSpine's reporting should always state retrieval budget, judge and reader (as the SOTA analysis already does). The OSS inability to set an observation date is the exact failure the MemSpine t_as/event-time design avoids.
  • Counter-lesson. Pure ADD-only with no validity model leaves contradiction handling to the reader (BEAM contradiction_resolution 35.7 / 32.5). This supports MemSpine's contest/supersede operators.
