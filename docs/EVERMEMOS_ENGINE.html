1. What is established, and what still needs measurement

The subject is EverOS (formerly EverMemOS), the open-source memory engine from EverMind. Package name everos, Apache-2.0, clone at EverOS @ fcd41b5 (2026-10-10), CHANGELOG head 1.4.1 (2026-09-24). Its tagline in code is a "md-first memory extraction framework": Markdown files are the source of truth, SQLite holds state and queues, LanceDB (or Milvus) is a rebuildable vector plus BM25 index (CLAUDE.md "Storage three-piece set"; docs/how-memory-works.md:26-39).

Two code bases. The repository EverOS is only the chassis: HTTP API, buffering, storage, scheduling, search orchestration. Every extraction algorithm (boundary detection, episode, atomic-fact, foresight, profile, reflection, rank fusion, agentic retrieval) and its prompts live in a separate library, EverAlgo (github.com/EverMind-AI/EverAlgo), consumed as everalgo-* PyPI wheels (pyproject.toml:90-109, docs/architecture.md:216-235). Earlier memspine notes (ECOSYSTEM_PROMPTS.md "OPAQUE-PROMPT NOTICE", S6d) record these wheels as closed. That is out of date: EverAlgo is public (shallow-cloned for this document, HEAD 7746a87, 2026-09-16, read only, never installed). Prompts quoted below are read from that repo.
Version skew. EverOS pins everalgo-user-memory==0.4.0, -agent-memory==0.4.0, -rank==0.4.1, -boundary==0.2.1 (pyproject.toml:91-109). EverAlgo HEAD is user-memory 0.8.0rc9, boundary 0.3.0. The prompt text I quote is HEAD. Behaviour that the EverAlgo CHANGELOG dates after 0.4.0 (model-written summary plus the summary-compress call, 0.5.0; profile prompt rewrite, 0.7.0) may not exist in the wheels EverOS actually installs. Stores and indexes

  • Markdown + YAML frontmatter: the memory content itself. read docs/how-memory-works.md:29-33. Daily-log files per kind, one user.md per user, a directory per skill.
  • SQLite (system.db, ome.db, ome.aps.db): unprocessed buffer, memcell ledger, cluster tables, cascade queue md_change_state, OME run records and counters, reflection reports. read docs/how-memory-works.md:75-79.
  • LanceDB (default; [index] backend = "lancedb", default.toml:56-58) or Milvus (remote only): vector ANN, BM25 (Tantivy), scalar filters in one engine. 1024-d vectors (EO/src/everos/infra/persistence/lancedb/tables/episode.py:17), embedding model default Qwen/Qwen3-Embedding-4B via DeepInfra (default.toml:128-138).
  • No graph database. Relations are only parent_id pointers (fact -> episode -> memcell) and SQLite cluster membership. read

How the stores combine at read time

  • Search reads only LanceDB (never the md or SQLite) except for the in-flight session buffer, which is returned verbatim when a session_id filter is given (read EO/src/everos/memory/search/manager.py:285-304).
  • Within LanceDB, the unit retrieved is the episode. Atomic facts are a second table used (a) to attach scored facts under episodes in the HYBRID path, (b) as MaxSim children in AGENTIC.
  • BM25 and vector scores are fused by RRF (k = 60 in hybrid and llm_multiround; k = 40 in agentic), then optionally LR-calibrated (section 8). No per-source weights are configurable at the API.
  • Profile is a KV lookup by owner: no ranking, one row, returned whole when include_profile=true (read EO/src/everos/memory/search/recall/profile.py:1-12).

Layers (DDD) and the everalgo boundary

read entrypoints -> service -> memory -> infra, enforced by import-linter (docs/architecture.md:29-61). Cross-cutting component/ (llm, embedding, rerank, tokenizer), core/, config/. EverAlgo is "stateless, no I/O, no prompts inline" per the architecture note (docs/architecture.md:229-233); EverOS only injects prompt overrides for two slots (config/prompt_slots/boundary_detection.yaml and episode_extract.yaml), both shipped empty and disabled, so the EverAlgo defaults run (EO/src/everos/service/_boundary.py:159, memory/extract/pipeline/user_memory.py:102; external confirmed by ECOSYSTEM_PROMPTS.md:29298-29299).

3. Complete insertion flow: accepted message to stored memory

  1. Receive messages

    POST /api/v2/memory/add with session_id and messages (sender_id, sender_name, role, timestamp, content[]). POST /memory/flush forces the boundary (is_final=True). Routes: EO/src/everos/entrypoints/api/routes/memorize.py:182,201. read

  2. Serialise per session

    memorize() takes a per-session_id lock around the whole read-merge-boundary-write cycle, under an asyncio.timeout of 360 s (service/memorize.py:229-237, default.toml:191). read

  3. Ingest and normalise

    ingest_process maps content items to a canonical message (memory/extract/ingest/service.py); multimodal items need the optional parser extra and a separate LLM (default.toml:114-126). read

  4. Optional defer

    defer_extraction=True only appends to unprocessed_buffer and returns (memorize.py:250-255, _boundary.py:96-116): zero LLM calls until a later /flush. read

  5. Buffer merge and the user-anchor gate

    Fresh messages are merged with the buffer (dedupe by message_id, sort by timestamp). In chat mode tool rows are dropped. If the batch has no role=user message and is not final, it waits in the buffer with no LLM call (_boundary.py:146-149,227-233,442-450). read

  6. LLM boundary detection (call 1)

    One batch call over the buffer decides all episode boundaries; the trailing segment stays in the buffer as tail unless is_final. A hard split applies at 65,536 tokens or 500 messages (default.toml:156-159). On ValueError (bad JSON) it retries up to 3 times (_boundary.py:239-287). read Mode default is agent (default.toml:167), which uses AgentBoundaryDetector, a filter-detect-remap wrapper over the same chat primitive (external EA/packages/everalgo-agent-memory/.../boundary.py:1-60).

  7. Persist memcell ledger

    Each cell gets id mc_<12 hex> and one SQLite memcell row with the full cell as JSON (_boundary.py:177-199,522-524). This row is the long-term replay source for profile extraction. read

  8. Dispatch pipelines concurrently

    UserMemoryPipeline.run (always) and AgentMemoryPipeline.run (agent mode) run under asyncio.gather (memorize.py:278-299). The user pipeline first emits UserPipelineStarted per cell, then extracts episodes. read

  9. Episode LLM call (call 2) and md write

    One generic episode call per cell (sender_id=None, the "cheaper" whole-cell template), retried up to 2 times plus a final attempt (user_memory.py:41,105-137,296-317). The result is copied md-only to every role=user sender in the cell (user_memory.py:140-178) and one EpisodeExtracted event is emitted per copy (:179-191). read The call to /add returns after the episode md is on disk.

  10. Background fan-out

    OME strategies subscribed to those events run asynchronously (section 4): atomic facts, clustering, profile, (foresight, off), (agent cases). The cascade daemon turns each md write into embedded LanceDB rows (section 5). read

Return value. MemorizeResult(message_count, status) with status accumulated or extracted (memorize.py:59-63,302-309). It reflects only the boundary and episode step. Atomic facts, profile and cascade indexing lag the response; a search right after /flush can miss them (docs/how-memory-works.md:249-274). read

Per-layer write stages

Episode (L1)

read Record = md entry with inline fields owner_id, session_id, timestamp, parent_type=memcell, parent_id, sender_ids and sections Subject, Summary, Content (user_memory.py:239-293). Cascade parses the entry, embeds Content and Subject concurrently, tokenises Content + Subject for BM25, and upserts the row keyed by content_sha256 (cascade/handlers/episode.py:56-123). Timestamp = cell timestamp = last message's time (boundary/chat.py:354).

Atomic fact (L2)

read Input is the episode text, not raw turns: aextract_from_text(event.episode_text, timestamp=event.episode_timestamp_ms) (extract_atomic_facts.py:47-50). All facts for one event are appended in one batched write with parent_type=episode (:62-107). Facts are therefore a derivative of the LLM-written narrative: an episode omission is never recovered at the fact level.

Profile (L4)

read Trigger path A (embedding available): ProfileClusterUpdated after geometry clustering; path B (no embedding): directly on EpisodeExtracted (extract_user_profile.py:102-125,212-218). Input is the raw memcell payloads from SQLite for clusters fresher than the stored profile (:128-209,306-320). Throttle constant PROFILE_EXTRACTION_INTERVAL = 1 (:74), i.e. every episode triggers a profile call per owner.

Cluster and reflection

read Each new episode is embedded again (a second embedding call, separate from cascade) as a size-1 cluster and merged into the nearest existing cluster by cosine 0.65 within 7 days (trigger_profile_clustering.py:84-128). Reflection (off by default) merges multi-member clusters, writes one merged episode, re-runs atomic facts, then soft-deprecates the originals in md and LanceDB (reflection/orchestrator.py:1-10,642-816).

Duplicate work on multi-speaker input (inferred from read code paths). The generic episode is generated once, but EpisodeExtracted is emitted once per role=user sender in the cell (user_memory.py:140-191) and extract_atomic_facts and trigger_profile_clustering run on each event. In LoCoMo every message is sent as role=user with its own sender_id (benchmarks/run.py:1403-1411), so each cell gives two identical episode copies, two atomic-fact LLM calls on identical text, and two profile calls per cell if profile is enabled. S6d counted "facts 1 per episode"; the code path suggests 2 per cell for two-speaker input.

5. Index creation: cascade and embeddings (the vector half)

  1. Watch

    read watchdog FS events, 500 ms debounce; plus a full scan every 30 s as a safety net (default.toml:217, docs/architecture.md:143-155). The benchmark disables the watcher and relies on the scanner (configs/locomo.toml EVEROS_DISABLE_CASCADE_WATCHER).

  2. Queue

    read Each change is a row in SQLite md_change_state; the queue is durable and replayed after a crash.

  3. Entry diff and embed

    read A handler per kind parses entries, hashes the content-bearing fields (content_sha256) and re-embeds only changed entries. Embedding is a soft dependency: without it, vector and subject_vector are None and the row is BM25/scalar-searchable only (handlers/episode.py:30-33).

  4. BM25 tokens

    read Tokenisation is done in the app layer (jieba for CJK) and stored as a space-joined *_tokens column; the LanceDB FTS index runs on that column with a whitespace tokenizer. Queries are OR-mode: each term is a SHOULD clause (recall/episode.py:56-72).

  5. Vector index

    read IVF_FLAT index only after 2,000 rows (default.toml:52-54); below that a query scans the column.

Embedding calls per stored cell (inferred from the handlers): 2 per episode copy (body + subject), 1 per atomic fact, 1 for the clustering embed per episode copy, plus 1 per query at read time. Embedding and reranker default to DeepInfra-hosted Qwen3-Embedding-4B and Qwen3-Reranker-4B (default.toml:128-154).

6. Transcript, buffering, IDs, and historical ingestion

What is stored verbatim

read Raw turns are held only in the SQLite unprocessed_buffer until a cell closes, then in the memcell.payload_json ledger as the full cell (_boundary.py:497-519). Search never reads the ledger; it exists to feed profile extraction (extract_user_profile.py:306-311) and OME replay. The searchable memory is the LLM-written episode text and the fact sentences. There is no verbatim-turn retrieval leg.

Identifiers and scope

read Partition key (app_id, project_id) then owner. Episode id <owner>_ep_<YYYYMMDD>_<NNNN>, fact id af_<date>_<n>, memcell mc_<hex> (tables/episode.py:31-37, _boundary.py:522). Every query predicate always includes owner, owner_type, app, project, and (for users) deprecated_by IS NULL (search/filters.py:60-72). Allowed request filters: session_id, parent_type, parent_id, timestamp, sender_id with AND/OR (filters.py:33-39).

Historical ingestion (how the benchmark loads LoCoMo)

  1. One EverOS server per conversation shard

    read servers = 10, each with its own store root (configs/locomo.toml, run.py:4473-4482).

  2. Per session: add in batches of 50, then flush

    read run_add_phase posts each LoCoMo session as its own session_id (locomo_conv<i>_s<n>), messages with the real session timestamp, all as role: "user" and sender_id = <speaker>_conv<i>, then calls flush (run.py:1370-1420). A failing batch is counted and skipped, not raised.

  3. Wait for drain

    read Polls cascade queue and OME run records until both are empty (run.py:863-1030, cascade_timeout = 7200). Image-only turns are skipped and captions dropped (stated in S6d; not re-checked here).

Production default is the same API with mode = "agent"; switching mode needs a process restart (default.toml:161-167).

7. Complete retrieval flow

  1. Request

    read POST /api/v2/memory/search: query, user_id | agent_id, method, top_k, filters, radius, min_score, include_profile, enable_llm_rerank. Default method = hybrid, top_k = -1 (cap) (search/dto.py:93-107). Five methods: keyword, vector, hybrid, agentic, llm_multiround (dto.py:31-50).

  2. Compile filters and validate components

    read Malformed filters give 422 before provider checks. Embedding is required for vector/hybrid/agentic/llm_multiround; rerank provider for agentic and agent-hybrid; LLM for agentic and llm_multiround; llm_multiround is user memory only (manager.py:214-221,831-941).

  3. Fan out by owner type

    read User: asyncio.gather(episodes, profile, unprocessed). Agent: cases + skills + unprocessed (manager.py:223-243).

  4. Run the chosen episode method

    read See section 8. There is no query rewriting in hybrid; rewriting exists only in agentic (multi-query) and llm_multiround (decider sub-queries).

  5. Shape and return

    read Episodes (subject, summary, episode text, timestamp in display timezone, parent ids) with optional nested atomic_facts (HYBRID only), profile, unprocessed buffer. Calibrated scores for HYBRID/AGENTIC are in [0,1] and emitted as recall-quality telemetry (manager.py:139-154,256-281). The engine returns structured items; it contains no answer prompt.

  6. Answer (caller)

    read Only the benchmark harness answers: benchmarks/run.py:1661-1690 renders each episode as "{subject}: {episode}\n---" under CONTEXT_TEMPLATE ("Episodes memories for conversation between A and B"), then the 7-step chain-of-thought ANSWER_PROMPT (adapters/locomo.py:96-165). Profile is omitted unless explicitly enabled.

8. Retrieval internals by method

8.1 HYBRID (API default): sparse + dense, RRF, LR calibration, heap-expand

  1. Parallel recall

    read BM25 over episode_tokens and cosine ANN over vector, pool size from top_k x multiplier (manager.py:429-431,805-822).

  2. Dual fusion

    read lr(dense, sparse) gives a calibrated per-episode score; rrf(sparse, dense, k=60) gives the expansion order (search/hierarchy.py:84-89; external functions in EA/.../everalgo-rank/.../fusion.py:27,46).

  3. Fact attachment

    read facts_for_episodes fetches up to max(2*top_k, 20) facts per episode by parent_id IN (...), supporting both new (episode entry id) and old (memcell id) parents (manager.py:439-446, recall/atomic_fact.py:1-14).

  4. Heap-expand with global competition

    read Episodes seed a top-N set. A heap ordered by RRF pops episodes; for each, up to 3 facts are LR-scored (cosine_to_lr_score against the parent's BM25) and enter the top-N if they beat its minimum. If any fact of an episode enters, the episode itself is evicted from the set. Loop stops after 10 consecutive no-change rounds (hierarchy.py:48-193). Result: a mixed list of facts and episodes under one score.

  5. Reshape and floor

    read reshape_hybrid_output nests facts under parent episodes; optional min_score floor (manager.py:454-457). No LLM and no cross-encoder: enable_llm_rerank is ignored on this path (module docstring, manager.py:11-14).

8.2 AGENTIC: cluster-scoped MaxSim with sufficiency check

read Pipeline "1:1 with the everalgo benchmark" (search/agentic.py:1-14): fact MaxSim (dense + sparse) -> hybrid_full -> cluster_scoped expansion -> agentic. Constants: 50 dense, 50 sparse, RRF k = 40, round-1 top 50 reranked to 10, round-2 cap 40, multi-query count 3 (agentic.py:55-70). Cross-encoder = Qwen3-Reranker with the instruction "Determine if the passage contains specific facts, entities (names, dates, locations), or details that directly answer the question" (agentic.py:72-76). Round 2 fires only if an LLM sufficiency check says the round-1 documents are insufficient (external SUFFICIENCY_CHECK_PROMPT_EN: checks entities, attributes, and dates of each document against the query), and then an LLM multi-query call writes 2-3 queries in three styles: keyword, natural question, hypothetical statement (HyDE) (external MULTI_QUERY_PROMPT_EN, strategies pivot / temporal calculation / concept expansion / constraint relaxation). Query-time LLM cost: 1 sufficiency call, plus 1 multi-query call when insufficient.

8.3 LLM_MULTIROUND: the method behind the published LoCoMo number

read benchmarks/configs/locomo.toml sets methods = "llm_multiround", top_k = 20. The loop (search/llm_multiround.py:1-45,679-902):

  1. Round 0: one block

    Embed the question; BM25 and vector recall (50 each, _SEED_CANDIDATES), fuse with RRF (k = 60), keep top 50 as one block labelled "original question".

  2. Decider LLM call

    The decider sees the QUESTION, CORE SO FAR (items already pinned, tagged with the sub-query that found them) and CANDIDATES THIS ROUND with one global index across blocks. It returns {"core":[idx...],"next_queries":[...]}. Instruction highlights: "favour RECALL over minimality"; a needed fact "is often an INCIDENTAL detail inside an episode about a DIFFERENT topic"; stop only when "the question is a SINGLE, self-contained fact AND the core you already hold answers it unambiguously" (llm_multiround.py:213-296). By default the decider reads each episode's summary; the LoCoMo config switches on EVEROS_LLMMR_DECIDER_FULL_TEXT=1 so it reads the full episode text (configs/locomo.toml [retrieval_env]; _decider_text at llm_multiround.py:589-602).

  3. Follow-up rounds

    Up to 3 follow-up sub-queries (max_subqueries) per round; each is recalled and RRF-fused independently (top 20 per sub-query) so a specialist hit is not diluted by consensus (default.toml:101-112). Stop when the decider returns no queries, when one follow-up round adds no new core (no_new_core_patience = 1), or at max_rounds = 3.

  4. Finalise

    Top-k = core first (hard guarantee), then each sub-query's top non-core candidate, then fill by max RRF score across sub-queries (_finalize_injection, llm_multiround.py:904-1030). No cross-encoder: the module header states the CE "was measured net-negative".

  5. Failure mode

    On 3 failed decider attempts (retries = 3, backoff doubling from 0.5 s) it falls back to the top 3 fused candidates as core and stops, logging an error, not raising (llm_multiround.py:360-400). A wrong decider model/endpoint pairing silently degrades to this fallback (comment at default.toml:89-92). Any published number must therefore state how many decider calls failed.

  • read Internal inconsistencies to flag: the adapter comment says its prompts are "byte-identical to the ones the published 90.58% was produced with" while the README says 94.42; configs/locomo.toml says "Our published numbers used qwen3.6-27B" as decider while the README table names deepseek-v4-flash-0731.   • read Reader and extractor are the same cheap model (gpt-4.1-mini extracts every memory, backbone_model); the decider is a separate, stronger or different model, so the "retrieval" step contains an LLM that has read the full episode text of 50+ candidates per question.

Vendor-run: 94.42, 93.05, 92.32. Competitor harness: 82.75 (cloud). Strict independent judge: 58.25. 14. Implementation findings and current limits

  • No write-time conflict resolution for facts. There is no ADD/UPDATE/DELETE/NOOP step on episodes or atomic facts. Only the profile (a separate document) has update/delete ops. read
  • Facts derive from the LLM narrative, not raw turns. The fact extractor reads episode text. Any detail the episode LLM drops cannot be recovered. read (extract_atomic_facts.py:47-50)
  • The published retrieval ignores most layers. The 94.42 configuration retrieves episodes only (decider-selected); profile off, foresight unused, facts not injected. read
  • Foresight is write-only. The repo itself says nothing reads it. read
  • Eventual consistency. Search reads LanceDB, which lags md by cascade time; benchmark harness must poll the queue. read
  • Silent degradation of the decider. A mismatched model/endpoint falls back to fixed top-3 core and reports a complete result; the code's own comment says twelve sweep arms were written up with this failure active. read (llm_multiround.py:360-390)
  • Per-sender duplication of facts/profile calls on multi-speaker input (section 4). inferred
  • Unauthenticated API. No built-in auth; defaults to loopback (default.toml:19-26). read
  • Cloud product vs OSS. OmniMemEval scored the EverOS cloud; the OSS engine's own scores are vendor-reported. read (SOTA doc)
  • Dependency on a fast-moving algorithm repo. Pinned wheels (user-memory 0.4.0) trail EverAlgo HEAD (0.8.0rc9); prompt behaviour in this document may not match an installed engine. external
  • Not examined: multimodal parsing details, knowledge-base pipeline call counts, Milvus backend, the Claude-Code plugin under use-cases/ (dead for the engine per ECOSYSTEM_PROMPTS.md).
