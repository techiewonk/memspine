1 · The loop

What MemSpine does on every turn

MemSpine is a memory engine for a chat agent. Each turn runs one loop: retrieve evidence for the question, compose it into the context window, let the model generate the answer, deposit the new turn and what can be learned from it, and later, during sleep, consolidate and personalise what was stored. The restructure split each stage into a v1 path (today's behaviour) and a v2 path behind off-by-default settings. A screen turns one setting (or one bundle) on and measures the change.

R Retrieve

Several search "legs" each return candidates; fusion merges them; the reranker reorders; the gate drops what the asker may not see or what is off-topic.

C Compose

Packs the chosen evidence into the window under a token budget, with rules that keep cited source turns, neighbours and standing answers.

D Deposit

Stores every turn raw, then extracts facts from windows of turns in one model call, checks each fact against its source line, resolves names, and decides replace / keep both / contest.

K Sleep

Background jobs that summarise sessions, mine facts, build the graph and communities, find patterns, keep value histories and decay old material.

T Trust

Tenant and owner scope, viewer checks, consent, erasure with re-derivation, the memory firewall and an audit chain. Mostly measured by tests, not QA accuracy.

X Runtime

Outbox, scheduler, cost ledger, caches, parallel legs. Expected to change cost and latency, never the answers.

Track A · Ingestion

How a turn becomes memory

Ingestion is everything between a user turn arriving and memory being searchable: the write path at turn time (D) and the sleep jobs that derive more from it later (K). It is reviewed separately here because its problems look different on LoCoMo: no question failed because a turn was not stored (stage a = 0 of 287), so ingestion matters through the derived memory it builds (facts, episodes, graph, summaries) that retrieval can then find.

2 · How a screen is run

Reading a screen result

Two kinds of run

  • J (reader only): memory is written, no sleep runs. Fast (about 10–20 min on the sample). Shows read-path settings only.
  • GC (with sleep): sleep jobs run with the model, so derived layers (facts, graph, episodes) exist. About 15 min each on the sample so far; needed for anything that reads derived memory.

Lesson from today: S10, S12, S13 changed nothing on J runs because their layers were never built. A 0/0 result on a J run means "not tested", not "no effect".

Rules and noise

  • PROMOTE: must beat the reference. NONINF: must not lose. PARITY: answers must not change. REPORT: describe only.
  • Samples are 60 LoCoMo questions (GC) or 80 (J), plus 60 OP-Bench where set. Each row shows questions gained / lost against the reference.
  • No run-to-run noise: two reference runs on the same commit gave identical answers on all 80 questions, so every flip is caused by the screen. The real limit is that random samples hold only 13–15 wrong questions; targeted slices (wrong questions of one class plus correct controls) now test whether a screen fixes what it aims at.

5 · What to choose

Recommended selection

Candidate configuration "v2-pick-1" (hypothesis to confirm)

Start from the reference arm (scr-pool-protect-jina, jina v3.5 reranker, Qwen3 0.6B embeddings) plus graph extraction during sleep (S02), and add only what has shown a gain or is designed to be safe:

  • read.gate_v2 (S20): the only screen with an interval above zero; expected to help OP-Bench irrelevance and LoCoMo category 5.
  • read.family_fusion (S14): +4/−1 on LoCoMo; confirm on the 437-question focus set (S51).
  • graph extraction in sleep (S02): +5/−1; already the base of every B5 screen.
  • Session summaries (S01): +3/−1; small but consistent with S02.
  • Runtime bundle (run-v2, S66): only if parity holds; it changes cost and latency, not answers.
  • Trust bundle (trust-v2): always on for production, judged by the safety suite, not by accuracy.

Hypothesis: LoCoMo focus accuracy from the 81.4% reference to about 83–85%; OP-Bench +4 to +8 points (mostly irrelevance); PrefEval and ConvoMem flat; MAB-CR flat until the write bundle is added.

Hold until the bundles report

Entity, episode and graph search legs (S30–S32) are within noise on 60 questions. Let the read-v2-graph bundle (S61) decide; only bisect if it moves.

Write path: test as one bundle

The window-facts arms lost on their own (S03 −4, S04 −6). The full write-v2 bundle (S62) adds grounding, coverage and integration, which target exactly those losses. Expect it to win on MAB-CR and lose a little on LoCoMo latency and cost.

7 · For discussion

Open questions

1 · Sample size

GC samples of 60 cannot separate ±2 from noise. Options: raise GC samples to 120 (doubles time) or send anything within ±3 straight to the 437-question focus set.

2 · Bundles or singles

Bundles answer "is v2 better" fastest. Singles answer "which setting". The current order runs bundles first and bisects only on a loss.

3 · Write path cost

With every write setting on, the estimate is 0.35–0.58 model calls per turn against a 0.19 target. Is accuracy worth that, or do we cap with the budget setting?

4 · Grounding gap

Grounding is 85.5% on CPU checks against a 95% target. Closing it needs one model call per window to judge non-English lines.
