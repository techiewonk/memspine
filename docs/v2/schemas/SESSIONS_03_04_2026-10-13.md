# Schema sessions 3 and 4: identity, evidence and lineage (owner, 2026-10-13)

These are sessions 3 and 4 of `SCHEMA_AGENDA.md`. They build on sessions 1 and 2 (`SESSIONS_01_02_2026-10-13.md`).

## Session 3: identity (ER-13 B)

| # | Question | Owner's answer |
|---|---|---|
| S3-1 | Entity key scope | **Tenant plus memory owner.** The owner is a user or a shared group, and every agent and session serving that owner sees the same entity. The session is recorded as provenance only. |
| S3-2 | Occurrence id | **`hash(source event id, sorted cited turn ids, assertion key)`.** Re-extracting the same turns gives the same id, so the step is idempotent. The same fact stated in a later turn is a new occurrence of the same assertion. |
| S3-3 | Retry (write) id | **Content plus source position, with client keys ignored:** `hash(scope, conversation/session id, turn index or source time, content)`. A true retry (the same turn sent twice) collapses and returns the original receipt. The same words in a later session count as a new write. The first answer was "content hash only". It was refined to this when that answer turned out to swallow genuine repeats and so silence the S4-3 "restated" signal. |

Identities stay separate (ER-13): the write (retry) id, mention id, assertion key, occurrence id and record id are distinct fields. The system authors all of them (S2-1). The model never does.

## Session 4: evidence and lineage (ER-11, ER-17, POL-2)

| # | Question | Owner's answer |
|---|---|---|
| S4-1 | Evidence roles | Each piece of evidence has one role: **support, binding or context.** *Support* states the fact. *Binding* resolves a pronoun, relative date or reference; these are the ER-11 context lines, and they must be cited. *Context* is shown to the model but never counts as evidence and never raises trust. |
| S4-2 | Source family | **The asserting principal.** For a person, this is the authenticated speaker or participant id. For a document, it is the author when known, otherwise the document. A tool's family is the tool name, and a web page's is its registrable domain. Derived records and assistant echoes inherit their parents' families through lineage, so a summary can never vouch for its own sources. |
| S4-3 | Same person repeating a fact | **A stability signal only.** It adds to a separate `restated` count, which is used for recency and conflict tie-breaks. It never counts as independent corroboration and never releases quarantine. |
| S4-4 | Quarantine release | **At least one other trusted family.** Release needs one family other than the writer's, at or above default trust (user, operator or system), stating the same content or key. External families (web, tool) can never release. This replaces today's check, which compares role, channel and message id (`engine.py:11393-11402`). Under that check a person can corroborate themselves. |
| S4-5 | Erasure of a source | **Hide, then re-derive.** Each derived record loses the erased parent. A record left with no live support parent is hidden at once and queued for re-derivation from its remaining sources. A record that loses only a binding parent is marked unbound and hidden. Summaries re-run without the erased input. |

## Effect on packages

- **F-01, F-16c:** entity keys use the tenant and the owner, and stop using the session. The separate identity fields are added.
- **W2-01:** a retry id from the content and source position; a duplicate returns the original receipt.
- **W2-06a and W2-08:** evidence roles and required binding citations, plus occurrence ids from cited turns.
- **F-16a and T5-04:** family inheritance through lineage, plus hide-then-re-derive on erasure.
- **The trust package that owns quarantine (corroboration):** the family-based release rule and the `restated` count. This is a behaviour change, so it is built flag-off and screened.
