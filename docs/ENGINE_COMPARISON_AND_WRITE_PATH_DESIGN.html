Four memory engines compared, and a write-path design proposal for MemSpine

Part A compares the combined engine (Graphiti + SimpleMem), MemSpine, Mem0 OSS v3 and EverOS (EverMemOS) stage by stage and layer by layer, states what each published LoCoMo number is made of, and lists the gaps. Part B proposes how MemSpine should use LLM calls at write time, one dedicated prompt per memory layer, for discussion before anything is built. Date of writing: 2026-10-11. Branch feat/local-qwen-stack. Nothing was run for this document: no GPU, no Ollama, no engine code from the other three projects was executed.

Read this first.
  • Proposal, not a result. Every number in Part B marked hypothesis is an assumed capture rate on a measured failure class, in the style of GAP_REGISTER.md. None is a measurement. Only measured and read in code items are facts.
  • Our LoCoMo runs use only the episodic layer. The adapter writes every turn as memory_type=episodic; no engine LLM role is bound in any shipped template or arm; sleep never runs. Every derived-memory feature (mined facts, graph, summaries, profile, agentic read) is built, opt-in and unscreened in a QA arm. The G-C2, G-C3 and G-C9 screens are written and queued, not run.
  • I80. All absolute MemSpine LoCoMo numbers (80.4, 81.4, 82.7 dev) come from a reader prompt that printed a gold answer; only arm-to-arm deltas that share the prompt stand. The clean re-baseline (Jina reranker + clean prompt, commit 888b888) has not been run.
  • Failure budget. Of 302 wrong answers in the 80.4 run: recall 69, cuts 61, reader 138, judge 11, gold errata 23, write path 0. Perfect retrieval gives about 87 (reader ceiling). Write-time layers can only attack the first two classes (130 questions, 8.4 points) and, indirectly, some reader detail and inference errors. Realistic expectations in section 6 are therefore small.
  • User constraints honoured: local reader only (Qwen3.5-9B, thinking off); LoCoMo categories 1-4 first (OP-Bench parked); designs generic and not LoCoMo-worded; jina-reranker-v3.5 for screens.

What each best score is actually made of

EverMemOS 94.42 (read in the clone's benchmark config, EM §11)
  • Write: gpt-4.1-mini writes every memory: one boundary call per add batch and one episode call per cell. The published retrieval uses episodes only: atomic facts are written but not injected (HYBRID attaches them; llm_multiround does not), foresight is write-only, profile is off (include_profile=false), reflection is off, no cross-encoder.
  • Read: a second LLM (the decider, a different and possibly stronger model) reads the full text of 50+ candidate episodes per round, up to 3 rounds, pins a "core" and issues up to 3 sub-queries per round; top-20 episodes are injected, core first. So retrieval contains an LLM that has read most of the candidate pool.
  • Answer and judge: a 7-step CoT prompt that tells the model to infer; a judge that credits topical overlap; category 5 removed.
  • Unknown: no ablation is committed, so the share due to LLM-written episodes versus the decider versus the answer prompt versus the judge cannot be separated. An outside-run version of the same engine (cloud) scored 82.75, a 12-point drop, and a strict judge gives 58.25.
Mem0 92.5 / 91.6 (doc + read in the OSS clone, M0 §1, §11)
  • Write: one LLM call per add() (ADD-only, bias to recall, facts of 15-80 words, both speakers, transition-aware), then spaCy entity linking. No segmentation, no summaries, no graph, no conflict handling.
  • Read: zero LLM calls: dense candidates, BM25 and entity boosts combined additively, top_200 memories (about 7k tokens) handed to the answerer. A wide net compensates for flat facts.
  • Platform extras: a temporal pass, timestamp parameter and other proprietary optimisations. The OSS code cannot take an observation date, so a historical replay resolves "yesterday" against the run date unless the harness injects the date into the message text.
  • Answer and judge: gpt-5 class models (per our file) with the community binary accuracy prompt. Same engine scores 77.7 in a neutral harness and 48.9 under a strict judge.
MemSpine 81.4 (measured, MS §12)
  • Write: nothing. One episodic record per turn; no LLM.
  • Read: Qwen3-Embedding-0.6B + BM25 + temporal + perspective legs, RRF, protected pool (top 3 per leg), 4B cross-encoder, keep 10, neighbours 2 before and 4 after, dated chronological lines, about 0.7-1.6k tokens per question.
  • Reader and judge: the same 9B local model. Accuracy with every gold turn present is 87.1%; with incomplete evidence 43.4%.
  • Derived layers contribute nothing to this number.
Combined engine (doc)
  • Nothing to decompose. Its design combines LLM-heavy write (about 20-25k calls on 5,882 turns, inferred) with an unfused three-block context. Whatever a "better result" on the other system came from, it needs summary.json, predictions.jsonl and manifest.json before it can be compared (COMBINED_ENGINE_COMPARISON §5 question 1).
What this means for write-time design. B5. Per-layer write design

B5.0 Principles that every layer obeys

  1. Raw turns stay authoritative. Derived records are additional rows with source.parents = the exact member turn ids. They are an index and a convenience, never a replacement. A hard forget of a turn removes its descendants (ADR-039; I72 parent-liveness re-check under the namespace lock).
  2. One write door and one prompt per layer, each bound to its own role under llm.roles and switched by its own flag. This is what makes isolated screens possible (one change per arm) and lets a future deployment give each role a different model, temperature or budget. Existing doors to reuse: the mined-fact deposit (_deposit_mined_fact) and _write_edge_fact paths, which already apply the firewall, trust cap, dedup and the I72 recheck.
  3. The unit of an LLM call is a session segment, not a turn. Segment = one derived session (30-minute gap) capped at about 1,500 prompt tokens, longer ones split with a 3-turn overlap. Reasons: coreference and relative dates need context (the combined engine's live vector window of 1 is a documented defect), Mem0 shows a whole-batch single call works, and call count drops by the session length (about 21.6 turns per LoCoMo session).
  4. Never per-turn LLM work on the user path. Inline work is rules only (embedding, firewall, perspective tags, reference edges). LLM work runs when a session closes (idle-debounced) or in sleep.
  5. Trust only goes down. A derived record's trust is at most the minimum over its parents; an inferred record never overrides a stated one (conflict.inferred_defers, I48); text from a quarantined or instruction-flagged turn is excluded from every extraction input; every model output goes through the firewall again on deposit (a model can be made to repeat an injection).
  6. Generic prompts. No dataset vocabulary, no gold-like examples (the gold lint of 8cebf97 covers prompts); examples use invented people and places; entity types and relation types are configuration, not baked in.
  7. Fail loudly and count. Each layer reports parse failures, retries, dropped-as-ungrounded items and calls per session in the run summary. A silent extractor failure must not look like "the layer did not help" (G-W13).
  8. Temperature 0, cache by (model, prompt version, input hash) (the existing mining_cache pattern), so a layer is built once and read-side arms reuse it.

B5.10 Layers that stay model-free

  • Prospective: no foresight call. EverMemOS writes up to 10 speculative predictions per cell and nothing reads them back (EM §14). The facts prompt already emits plans with a date window and auto_watch turns a plan naming a future date into a due watch. Speculation stored as memory also conflicts with A08 ("never store an inference as a fact").
  • Working / persona: set by the caller; versioned. Resource: chunks at trust 0.3; extract@document has no call site and stays unwired. Associative: links by embedding similarity and rules (rule_edges); "no LLM proposes links" stays. Shared: grants and subscriptions are bookkeeping.

B5.11 Cross-layer ranking at read time (G-C4: do not flood the context)

The failure to avoid is the combined engine's: three independently ranked blocks concatenated, no global rank, no dedupe. The failure to also avoid is ours from the reranker screens: more tokens is not free (rerankers cut context 35-60% for 1-2 points). Proposal: derived layers decide candidacy; raw turns remain the evidence the reader sees.

  1. Each layer contributes legs. Raw: vector, lexical, temporal, perspective (existing). Episode: episode_vec, episode_bm25. Fact: fact_vec, fact_bm25, view_tags. Graph: graph, graph_nodes. Summary: summary_vec (lifted narrowly).
  2. Evidence lifting. A hit on a derived record is converted to its parent turn ids. A turn's fused score is the sum over legs of 1/(k + rank) for the units whose lift includes it, with legs grouped into families (raw, episode, fact, graph) and each family counted once per turn (the existing pool_protect_mode: source_family logic, R02), so correlated votes are not double counted and a turn found by two independent families rises.
  3. Protected slots per family. After the fused cut, the top p units of each family (lifted to turns) enter the pool whatever the fused rank, exactly as pool_protect_per_leg: 3 did for raw legs (+15 net on 1,540, about 30% more rerank cost). Pool growth is bounded by families x p.
  4. One reranker, one document type. The cross-encoder (jina-reranker-v3.5 for screens) scores (question, dated raw turn) for every candidate. Mixing narrative and turn documents in one min-max distribution would let long narratives dominate; episode text as a rerank document is a separate later arm.
  5. Assembly with budget shares. Raw windows keep at least 70% of the 4,096-token budget (existing replay windows). A notes block takes at most 20%: at most 5 derived records (facts, edge lines with validity, episode summaries) chosen by their own leg score, each shown as [note, from turns 12-14] ..., and dropped when all its parent turns are already in the context and its text adds fewer than 30% novel content words. A profile / session-summary block takes at most 10% and is relevance-gated. The header-share validator (shares sum below 1) already exists.
  6. Derived-only evidence is capped at 3 notes whose parents are absent from the context (they cost tokens without raw support). A derived record can never be the only thing between the reader and an abstention: if the reranker's raw score for every parent is below the store-calibrated floor, no note is shown.
  7. Everything is logged in forensics: per-family ranks, lifted units, notes shown, notes dropped as redundant, tokens by block. Reject a design if mean context tokens per question rises more than 30% over the same-reranker control without a net gain.
Two hypotheses are kept apart on purpose. H-index: derived records improve what is retrieved while the reader sees raw dated turns. H-note: derived text improves what the reader understands (resolved pronouns, dates, transitions). A screen arm exists for each; EverMemOS's result is evidence for H-note (the episode is the context), the failure mix of our own 80.4 run (recall and cuts 43%, reader 46%) is the reason to test H-index first.

B8. Open decisions for you

  1. When do write-time LLM calls run? Options: (a) inline per turn; (b) at session close, idle-debounced, plus sleep for cross-session work; (c) sleep only. Recommendation: (b). Inline per turn gives each call one turn of context (the combined engine's live window of 1, a documented defect), 22x the calls, and puts model latency on the write path. Sleep only delays visibility to the next cycle and cannot serve a conversation that continues. The engine needs a real session-closed hook (today session_end behaves like a sleep sweep).
  2. Unit of one call. Options: per turn; per fixed window of N messages (Mem0 style); per derived session segment of at most about 1,500 tokens. Recommendation: per segment.
  3. Which layers first. Options: facts; episodes; graph; summaries. Recommendation: S1 facts, S2 summary + profile block, S3 graph (all three arms are already built and queued), S4 episodes (build in parallel, screen after S1 tells us what a derived leg can do). Rationale in B6.4.
  4. Acceptable ingest-time cost. Options: at most 0.1 calls per turn (facts + summary, about 1 h); at most 0.25 (S1-S4, about 3 h per full LoCoMo store, cached); at most 0.35 (with profile and reflection). Recommendation: 0.25 calls per turn and 3 GPU-hours per full 10-conversation ingest for screens, with the cache making repeat arms free; production budgets set per deployment.
  5. Episode as the retrieval unit, or alongside raw turns? Options: replace raw-turn retrieval with episodes (EverMemOS); add episodes as legs lifted to raw turns (H-index); show episode text to the reader (H-note). Recommendation: alongside, H-index first, then H-note; never replace. DECIDED DESIGN (2026-10-11): adaptive window + three call slots, rollout step 1 built

The user approved a narrower design than the per-layer proposal of B5: one structured call per adaptive window with separate per-layer sections (call 1), a session-close slot (call 2, interface only) and the sleep slot (call 3, existing stages). Budget: at most one call per turn on the user path, target about 0.2 to 0.3. Rollout step 1 is built and opt-in (write.window_extract: facts, default off): the facts section feeds the semantic layer as a retrieval leg through the G-C2 machinery (view_tags leg, atomic_fact records, parents = the cited turns). The graph and episode sections are built and individually toggleable, default off. Nothing was run on a GPU or on Ollama; the arm evals/arms/scr-window-facts-jina.json is written and not launched. Decision record: docs/adr/ADR-066-adaptive-window-write.md. Register rows: GAP_REGISTER.md section M.

D4. Safeguards

  • Per-section fail-closed. The reply is parsed once (the I69 repair net and optional retry apply). Each section is then validated alone: a section that is not the expected shape is dropped and counted; an item that fails its schema is dropped and counted; the other sections still land. A reply that names no section at all drops all of them.
  • Grounding. A fact must cite at least one valid line and quote a span that occurs, word for word (case, punctuation and spacing ignored, word order kept), in a cited line; otherwise it is dropped as ungrounded (facts_ungrounded, with facts_uncited for the no-citation case). An edge must cite a valid line. An episode with no valid citation keeps the whole window as its evidence and is counted (episodes_uncited).
  • Split mode. window_split: auto turns the one call into two (facts+edges / episode) once a quarter of the last 8 joint calls failed to parse or had a malformed section; always and never are the manual settings. Only meaningful with more than one section enabled.
  • Cache. Each call is cached by (model, prompt version with its partials digest, section group, window text, participants). A repeat on the same history makes no call (cache_hits). The cache is the engine KV cache: in memory per process unless a durable backend is configured. A forget deletes the cached replies of windows that held the erased turn.
  • Derived records follow the rules of every derived record. Parents = the cited turns, so the forget cascade (ADR-039) removes them; the same write door as a mined fact (firewall, trust capped at the least trusted parent, non-privileged assistant role, dedup, conflict ladder); a fact is tagged atomic_fact, window_fact, mined:win:<window> and the view tags (person:, loc:, topic:) so the existing view_tags leg and list cards see it; the speaker tag is inherited only when the cited turns share one speaker. An episode fragment is a semantic record without entity or attribute (always ADDed), channel window_episode, tagged episode_fragment, never a source for graph extraction.
  • Isolation. One segmenter, queue and edge buffer per namespace; a window holds the turns of one session of one namespace; nothing is shared between stores, including the topic level (tested with interleaved writes of two users).
  • Inputs. Quarantined and instruction-flagged turns, and turns no longer live, never enter a window.
  • Generic. The prompt has no dataset vocabulary and no gold-like example (the gold lint scans it); the date example is a placeholder. Edge types and entity types are configuration (extract_graph.relation_types), not baked in.

D8. What is not built, and what the screen can and cannot tell

  • Call 2 content (summary, stitched episode narrative, profile operations), the episode as a retrieval leg and the neighbour-aware extraction (G-W4: the extractor sees only its own window, not earlier facts) are not built. Window context does cover the coreference and relative-date part of G-W4.
  • The edges and episode sections have fake-LLM tests only. The facts section is the only one with a screening arm; the prompt has never met a real model, so its JSON quality (and therefore the split-mode rate and the ungrounded rate) is unknown until the first run. The counters exist so that a silent extractor failure cannot look like "the layer did not help".
  • Confounds to read in the first screen: the sleep cycle's consolidate stage also writes an extractive summary per session into the pool (as in the GC arms), the window facts duplicate nothing of mine_facts (off in this arm) but are mined from 6-turn windows instead of whole sessions, and the topic boundary is learned per conversation.
